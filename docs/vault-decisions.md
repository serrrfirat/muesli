# Vault decisions — issues #6, #9, #12 and encrypted queue for #7

## Implementation and invariants

Feature implementation is limited to `Vault.swift`; the integration owner supplies UI, binary commands, issue evidence, and E2E verification. No unit tests or child-agent builds were run.

- Storage is **CryptoKit AES-256-GCM encrypted JSON, not SQLite or SQLCipher**. A versioned envelope contains only format metadata and base64 ciphertext (combined nonce/ciphertext/tag). Meeting titles, notes, transcripts, timestamps, embeddings, identifiers, and queued audio are all inside the authenticated ciphertext. This is a maintainable local implementation without a bundled native database dependency. A SQLCipher replacement must explicitly migrate authenticated snapshots and preserve backup compatibility or version the format; it is not implemented or claimed here.
- Each write uses a fresh random GCM nonce. Additional authenticated data includes a domain separator, format version, purpose, backup salt, and KDF iteration count. Vault and backup ciphertext cannot be interchanged. Unknown versions, invalid keys, truncated files, malformed JSON, authentication failures, duplicate identifiers, nonfinite vectors/times, and invalid time ranges fail closed.
- The dedicated root is mode `0700`; files are created mode `0600`. Reads refuse final-component symlinks and nonregular files. Writes create a same-directory exclusive `0600` temporary file, fully write and fsync it, close it, then rename it atomically. Temporary files contain only ciphertext (except the explicitly test-only key). The rename is the commit point; directory fsync is best-effort because some volumes reject it. Pre-rename errors leave the prior snapshot intact. Atomic replacement is guaranteed; strongest sudden-power-loss durability depends on the filesystem.
- One coordinator owns each directory. An `NSLock` serializes operations on an instance; this is not a multi-process database. Two simultaneous independent vault owners are unsupported. Each operation reloads the authenticated snapshot rather than maintaining a stale in-memory index.
- Reads and writes are bounded at 512 MiB per encoded file. Large collections or extensive offline audio may exceed this limit; errors are explicit, never reported as successful persistence. Whole-snapshot encryption and in-memory search suit local moderate collections, not a large streaming archive. Audio plus JSON/base64 overhead consumes capacity faster than raw audio size.

## Keys and backups

- Normal mode uses a random 256-bit data key in the macOS login Keychain, under service `PrivateGranola.Vault.v1` and an account derived from the dedicated directory's SHA-256 path. The key is nonsynchronizing and requests `WhenUnlockedThisDeviceOnly` accessibility. Keychain errors propagate; no filesystem or mock fallback exists in production. A moved vault needs the original Keychain account or a backup restored into a new root. Production Keychain permission behavior must be exercised by the packaged binary.
- Test mode alone uses `test-vault-key.bin` in the supplied isolated root; this **intentionally plaintext, test-only key** is the exception to the no-plaintext-files policy. It is not a production secret store and makes that test root decryptable by its owner. Normal mode never reads it. Missing keys for an existing vault fail without generating a replacement key or overwriting data. A malformed key fails without regeneration.
- Backups contain the same complete snapshot, including pending audio. They are encrypted and authenticated with a separate 256-bit key derived using CommonCrypto PBKDF2-HMAC-SHA256, a fresh 256-bit salt, and 600,000 iterations. The iteration count is fixed for version 1 and checked before expensive derivation. This is password stretching, not a memory-hard KDF; weak user-selected passwords remain vulnerable to offline guessing. The generated high-entropy phrase is recommended.
- `generateRecoveryPhrase()` returns `pg1-` followed by eight hyphen-separated groups of eight lowercase hexadecimal digits: **256 bits from `SecRandomCopyBytes`**. It is not BIP39, has no dictionary/checksum, and has no wallet/on-chain meaning. The phrase is never stored in the snapshot. Passwords and phrases are interpreted as exact UTF-8 bytes, without trimming or Unicode normalization; callers must not silently alter them. Any nonempty password up to 4,096 UTF-8 bytes is accepted; save the generated phrase securely outside the vault.
- Restore reads, validates the envelope, derives the backup key, authenticates/decrypts, decodes, and validates the entire snapshot before encrypting it under the current local key and atomically replacing the live file. Wrong phrases, corrupt ciphertext, and invalid schema leave the live bytes unchanged. Export refuses destinations resolving to the live vault or test key. No plaintext backup/staging file is created.
- These protections address at-rest confidentiality and authenticated integrity, not deletion/rollback by an attacker who can replace files, a compromised running process, or encrypted data on a maliciously substituted directory. Secrets necessarily exist in process memory during use; no memory-erasure guarantee is claimed.

## Offline audio queue

`appendPendingChunks(_:meetingID:)` atomically merges new audio under the vault lock, preserving concurrently appended chunks and excluding already-transcribed IDs. `pendingChunks()` preserves chunk IDs, channel, timing, MIME type, and bytes. `commitTranscription(_:meetingID:)` merges a transcript into the latest meeting and acknowledges only that chunk in the same encrypted commit. Deleting a meeting removes its queued batch; active or unpersisted recording meetings cannot be deleted.

The queue lives in **the same authenticated `vault.pgenc` snapshot**, rather than a separate `pending.enc`. Backup/restore and meeting deletion therefore commit meetings and queued audio in one atomic replacement. Live chunks synchronously finish their encrypted append on the off-audio chunking queue before returning; MainActor tasks only refresh the UI and schedule uploads. Stop/quit await recorder drain rather than using `Task.yield` as a persistence barrier. Canceled uploads leave unacknowledged audio recoverable. Retry reuses chunk IDs; storage does not itself transmit or schedule retries. No raw-audio filesystem API or plaintext cache is provided.

Microphone consent precedes provisional meeting creation. The model reserves a writable encrypted meeting before device capture begins; a failed or canceled startup atomically removes only an untouched provisional meeting with no queued audio, transcript or user work. If a live encrypted append fails, chunks are retained in a synchronized session ledger and recording stops. Stop retries their persistence; continued failure is visible and normal application termination is refused. Forced process termination or machine failure cannot preserve genuinely unwritten memory-only audio. A normal, successful silent recording is not discarded as a failed startup.

## Search semantics

- Full-text search scans titles, summaries, scratch notes, and all transcript segments locally. Tokens are case- and diacritic-insensitive alphanumeric words. All query tokens must be present somewhere in the meeting. Weighted term frequency ranks title hits over summary, scratch notes, then transcript; exact normalized phrase presence adds a bonus. Empty/punctuation-only queries list all meetings. This is deterministic lexical relevance, not linguistic stemming, fuzzy matching, or a remote search service. Nonspace-delimited language tokenization is limited to the same alphanumeric-word rule.
- Semantic search computes cosine similarity locally in `Double` over persisted `Float` embeddings. A meeting's score is its best matching embedding. Mismatched dimensions and zero-length-magnitude stored vectors are excluded; the query must be nonempty, finite, and nonzero. Results sort by descending similarity, then newest date and stable UUID. Negative similarity is retained rather than silently hidden. Embeddings must come from the same model/space as the query; dimension agreement alone cannot establish that, and `Meeting` currently has no embedding-model identifier.

## Required binary E2E evidence (integration owner)

1. Save two distinguishable meetings with transcripts, scratch notes, summary, timestamps, embeddings, and a pending audio batch. Exit and relaunch the actual binary with the same isolated root; compare every field and audio byte, not only counts.
2. Export with the generated phrase; modify/delete local content and queue, restore, then relaunch and compare the exact original snapshot. Also restore into a separately keyed new root. Exercise an ordinary password separately.
3. On a populated vault, attempt restore with the wrong phrase and a backup whose decoded sealed payload is byte-flipped/truncated. Verify explicit errors, unchanged live-file bytes, and unchanged content after restart. A modified salt/version/iteration field must also be rejected.
4. Flip ciphertext in the live file and relaunch; verify a hard failure and no empty-vault replacement. Remove/corrupt the isolated test key and verify no automatic key regeneration for an existing vault.
5. Scan app-owned files and backup for unique title, transcript, note, and audio sentinel bytes. They must be absent; only the documented isolated test key is plaintext. Verify filesystem modes.
6. Check lexical relevance with title-vs-transcript hits, case/diacritic variants, multiword AND narrowing, and no-match input. Check semantic ordering for aligned, orthogonal, and opposite vectors; reject zero and nonfinite queries. Restart and repeat rankings from persisted vectors.
7. Fail mock transcription after encrypted queue persistence; restart, read/retry the same chunk IDs, save completion, and clear the queue. Confirm backup restores the pending bytes and deleting a meeting clears its queue.
8. In normal mode launch the actual packaged binary, exercise Keychain creation/reuse, exit/relaunch, and verify no file data key is produced. Locked/denied Keychain must error, not switch to test storage.

No verification outcomes are asserted here; project-wide and binary-driven checks are owned by the integration agent.
