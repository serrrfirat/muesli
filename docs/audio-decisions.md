# Audio capture and meeting detection decisions — issues #3, #4, and #7

## Scope and contracts

Feature implementation approved by the delegated assignment. Read `docs/DECISIONS.md` and `Models.swift`; there was no existing Audio.swift or audio convention to preserve. Only Audio.swift and this decision note are owned by this slice. No unit tests, builds, formatters, or mid-flight checks are run here: the integration owner runs the binary E2E after all slices land.

`AudioRecorder.start` captures the actual microphone using AVAudioEngine and actual other-process output using a private Core Audio process tap plus a private aggregate device. It excludes the app's process and does not mute playback. Either channel failing setup fails recording and tears down both channels. It never falls back to a generated signal, a file, ScreenCaptureKit, or microphone-only success. `stop` drains already captured buffers, emits final audible chunks, and releases the microphone tap/engine, IOProc, aggregate, process tap, health monitor, and observers. Runtime processing/device failures stop capture and are exposed through optional `onFailure` and a subsequent throwing `stop`.

Microphone permission is requested using AVFoundation. The app bundle must contain `NSMicrophoneUsageDescription` and `NSAudioCaptureUsageDescription`. Core Audio process taps require macOS 14.2+. System tap creation/start failures include their OSStatus and privacy guidance. No private TCC API or system security configuration change is used. A quiet system stream is not evidence of permission approval: the public process-tap API does not provide a reliable separate authorization-status query. Successful tap setup alone must not be presented as proof of captured system audio. Prove it by playing another process's known sound and observing a non-silent `.them` chunk. OS-supplied silence cannot safely be distinguished from a muted/quiet source or denied/revoked access using waveform data alone.

## Meeting detection hint — issue #7

`AudioRecorder.activeMeetingApps()` reads the public Core Audio process list, active input-stream flag, PID, and (only if a running app identity is unavailable) bundle ID. It maps those identities to the display names of Zoom, Microsoft Teams, Safari, Chrome, Edge, Firefox, and Brave, including identifiable browser helpers. It ignores this app and unknown processes, deduplicates names, and returns an empty result when enumeration fails or an individual process cannot be inspected. It reads no window titles, URLs, page content, messages, or audio samples, requests no permissions, and does not create a tap. Ambiguous WebKit helpers are not attributed to Safari.

This is a best-effort hint that a known meeting-capable app has an active microphone stream, not confirmation of a meeting: dictation or another non-meeting microphone use can trigger it, while muted calls and unidentifiable helper processes may not. The parent owns periodic polling and an explicit consent prompt, never automatic recording. If this OS restricts these public metadata queries, the helper supplies no hint rather than bypassing permissions.

Parent binary E2E should inspect an idle state and, when a user-authorized real meeting-capable app has an active microphone stream, verify its app-name hint and consent prompt without recording before consent. No unit tests or child-side checks were run for this addition.

## Chunk boundaries and encoding

- Each channel has an independent chunker and bounded preallocated callback handoff. Exhausting that handoff fails recording rather than silently dropping samples. Chunking, WAV encoding, and consumer callbacks run away from audio callbacks. `onChunk` must not perform slow blocking work; enqueue transcription instead.
- Both live capture and `chunkFile` use the same sample-clock chunker. File decoding is AVAudioFile Float32 PCM; multichannel input is averaged to mono. This is a speech-transcription choice: stereo spatial information is discarded, and perfectly opposite-phase channels can cancel. The `.me`/`.them` label is semantic source identity, not a WAV stereo channel.
- Output is playable little-endian PCM16 mono RIFF/WAVE (`audio/wav`) at the source's integral sample rate. In-memory encoding avoids plaintext temporary audio files. Captured audio never goes to disk within Audio.swift.
- Energy is measured in approximately 20 ms windows. RMS below 0.003 (about −50 dBFS) is treated as silence. Leading silence is omitted. A pause of at least 600 ms closes the chunk; at most 200 ms of trailing silence is retained. The first active window is retained in full; there is no additional pre-roll. This deliberately trades very quiet speech retention for eliminating all-silent transcription requests; it is not ML speech detection.
- Continuous audio splits at exactly the earlier of 30 seconds or `(25,000,000 − 44) / 2` PCM samples, so the WAV including its 44-byte header never exceeds the 25 MB decimal upload boundary. No over-limit append occurs. Entirely silent chunks are suppressed, and an entirely silent imported file is rejected explicitly.
- `start` and `end` are seconds in the original source timeline, not concatenated voiced duration. Files start at frame zero. Live channels share a monotonic host-clock epoch; discarded silence remains a gap. Timestamp discontinuities greater than 100 ms flush rather than collapse gaps. Microphone configuration changes stop capture; a one-second system-device/format health monitor catches unavailable devices and output format changes, requiring restart rather than an implicit channel loss.
- Supported capture PCM is Float32 at integral rates up to 768 kHz. Unsupported hardware formats, malformed file decoding, missing input devices, or callback buffers above the bounded capacity are explicit errors. A file chunking call returns all chunks by contract, so imports of extremely long files retain their resulting encoded chunks in memory.

## Binary E2E scenarios for the integration owner

These are required scenarios, not claimed results. No test execution has occurred in this slice.

1. Import a known fixture containing 1 s leading silence, 1 s tone/speech, 1 s silence, and 1 s tone/speech. Decode every resulting WAV with AVAudioFile or an actual media decoder; check RMS is nonzero, sample rate/PCM16/mono are correct, semantic channel is `.them`, time gaps remain, and decoded duration matches `end − start` within one sample. Expect two chunks, with starts near 1 and 3 seconds and approximately 200 ms trailing silence on the first.
2. Import the same fixture with `.me` through the binary's audio diagnostic interface and check channel identity, not a separate chunker implementation. Import an all-zero file and corrupt/non-audio input; require explicit failure without any transcript/chunk success.
3. Import a 65 s continuous fixture. Expect three playable chunks, boundaries at 30 and 60 seconds, monotonic original times, each duration at most 30 s and each WAV at most 25,000,000 bytes. Exercise a high-rate WAV (at least 441 kHz) to make the byte cap stricter than the duration cap; check contiguous sample-accurate boundaries and all output sizes.
4. In the actual packaged app, start/stop twice while speaking and playing known sound from another process. Require both `.me` and `.them` non-silent playable outputs, no app playback recapture, and no microphone-use indicator/private aggregate/process tap left after stop. Exercise stopping mid-speech to prove final chunk delivery. Enumerate Core Audio tap/aggregate properties before and after if available to the diagnostic interface.
5. Deny microphone access through an already denied environment, or choose an environment with no usable microphone. Record must report the actual permission/device error and must not import fixtures or report a successful recording. Do not alter system security settings to manufacture this test.
6. Denied system-audio permission must produce an actual Core Audio failure if the OS exposes one; if this OS supplies silence instead, record the API limitation and absence of a `.them` chunk as unverified capture, not a pass. The E2E fixture path does not validate TCC or replace this scenario.
7. Disconnect/switch a capture device while recording where a human-controlled environment permits it. Require runtime error, resource teardown, and a successful later fresh start with a usable configuration.

Microphone/system-audio E2E requires a logged-in GUI session, actual input/output devices, the real `.app` bundle, and user-granted OS permissions. Automated fixture ingestion requires none of those permissions but proves only decoding/chunking/encoding. The parent owns dedicated issue evidence and the ten-failed-E2E-attempt escalation rule.
